# Phase 1 Database Design Contract

Status: APPROVED AND LOCKED through Phase 1A.2

This document is authoritative for Phase 1B migration authoring. It refines the
approved Phase 0 architecture without changing its trust, financial, inventory,
payment, storage, or authorization boundaries.

## Phase 1 Scope

Phase 1 establishes the minimum database, authorization, and storage foundation
for authenticated commerce. It does not implement application features,
Realtime delivery, returns, refunds, shipments, notifications, reviews, or
promotions.

The final Phase 1 schema contains exactly 22 tables:

```text
public.profiles
private.user_roles

public.categories
public.products
public.product_variants
public.product_options
public.product_option_values
public.variant_option_values
public.product_images

public.inventory
public.inventory_movements
public.inventory_reservations

public.carts
public.cart_items

public.addresses

public.orders
public.order_items
public.order_status_history

public.payments
public.payment_submissions
public.payment_events

public.audit_logs
```

No other table belongs in the Phase 1 baseline.

## Supabase Key Model

Canonical application environment variables are:

```text
Browser:
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY

Server:
SUPABASE_SECRET_KEY
```

The publishable key may enter browser code and operates under grants and RLS.
The secret key is backend-only, bypasses RLS, and therefore never replaces
explicit request-level server authorization. Legacy `ANON_KEY` and
`SERVICE_ROLE_KEY` names are not canonical application configuration. Supabase
database roles such as `anon`, `authenticated`, and `service_role` remain
platform concepts used by grants.

## Global Data Conventions

- Application entity PKs are UUIDs generated by PostgreSQL with
  `gen_random_uuid()`.
- `profiles.id` reuses `auth.users.id`.
- Pure join/ownership tables use natural composite keys where stated.
- UUID opacity is not an authorization boundary.
- Timestamps are `TIMESTAMPTZ`; event/history rows use database `created_at`.
- Mutable rows use one shared `updated_at` trigger function.
- Statuses use `TEXT` plus `CHECK`, not PostgreSQL enums.
- Required text fields reject blank values.
- Business rows use archive/status transitions instead of routine deletion.

## Money and Currency

All authoritative monetary values are `BIGINT` minor units. Floating-point and
PostgreSQL `money` types are prohibited.

Currency is persisted as uppercase ISO-style text:

```text
currency_code TEXT NOT NULL DEFAULT 'PHP'
CHECK currency_code matches exactly three uppercase letters
```

Initial currency is `PHP`. Required monetary fields are:

```text
product_variants.price_minor
product_variants.compare_at_price_minor
orders.subtotal_minor
orders.discount_minor
orders.shipping_minor
orders.total_minor
order_items.unit_price_minor
order_items.unit_discount_minor
order_items.line_subtotal_minor
order_items.line_discount_minor
order_items.line_total_minor
payments.amount_minor
payment_submissions.claimed_amount_minor
```

Amounts are nonnegative. Compare-at price, when present, is not less than the
sale price. Line and order equations are checked in rows where possible and
cross-row totals are verified in the authoritative checkout transaction.

## Identity and Roles

`auth.users` is canonical identity.

`public.profiles` contains `id`, optional `display_name`, optional `phone`,
`created_at`, and `updated_at`. Its PK is an FK to `auth.users(id) ON DELETE
CASCADE`. It contains no role, credential, or duplicated authoritative email.

`private.user_roles` contains `user_id`, `role`, optional `assigned_by`, and
`created_at`. Its PK is `(user_id, role)`. Allowed roles are `customer`,
`admin`, and `super_admin`.

One hardened `AFTER INSERT` trigger on `auth.users` atomically creates the
minimal profile and fixed `customer` role. Signup metadata may supply only
allowlisted presentation fields and can never assign privilege.

Customers cannot mutate roles. Privileged changes require a trusted,
MFA/AAL2-authorized `super_admin` operation, last-`super_admin` protection, and
an audit row. The first `super_admin` is bootstrapped with one explicit trusted
transaction against an exact Auth UUID; no production identity or credential is
stored in migrations. Local deterministic bootstrap data belongs only in local
seeds.

## Catalog

### Categories

`public.categories` contains `id`, optional `parent_id`, lowercase unique
`slug`, `name`, optional `description`, nonnegative `position`, optional
`archived_at`, `created_at`, and `updated_at`.

`parent_id` references categories with `ON DELETE RESTRICT`, cannot equal the
row ID, and category writes must reject hierarchy cycles. V1 uses one primary
category per product; no product/category join table exists.

### Products and Variants

`public.products` contains `id`, optional `category_id`, lowercase unique
`slug`, `name`, optional `description`, `status`, `created_at`, and `updated_at`.
Product statuses are `draft`, `published`, and `archived`.

`public.product_variants` contains `id`, `product_id`, normalized unique `sku`,
optional `name`, `price_minor`, optional `compare_at_price_minor`, `status`,
`created_at`, and `updated_at`. Variant statuses are `active`, `inactive`, and
`archived`. Every sellable product has at least one variant, including an
optionless default variant.

### Product Options

`public.product_options` contains `id`, `product_id`, `name`, `position`, and
`created_at`. Option names are case-insensitively unique per product.

`public.product_option_values` contains `id`, `product_id`, `option_id`,
`value`, `position`, and `created_at`. Values are case-insensitively unique per
option.

`public.variant_option_values` contains `product_id`, `variant_id`, `option_id`,
and `option_value_id`. Its PK is `(variant_id, option_id)`. Composite FKs prove
that the variant, option, and value belong to the same product and prevent two
values for one option on one variant.

### Product Images

`public.product_images` contains `id`, `product_id`, optional `variant_id`,
unique `storage_path`, required `alt_text`, nonnegative `position`, and
`created_at`. A null variant identifies a product-wide image. Composite FKs
prevent cross-product variant images. Store paths, never generated URLs.

## Inventory

V1 has one inventory location and one `public.inventory` row per variant. No
warehouse, location, or branch table exists.

`public.inventory` contains `variant_id` as PK/FK, `on_hand`, `reserved`,
`safety_stock`, and `updated_at`. Required invariants are:

```text
on_hand >= 0
reserved >= 0
safety_stock >= 0
reserved + safety_stock <= on_hand
available = on_hand - reserved - safety_stock (derived, not persisted)
```

Persisting `reserved` is justified by concurrency-safe conditional updates. It
must agree with active reservation totals after every inventory transaction.

`public.inventory_reservations` contains `id`, `order_id`, `variant_id`,
positive `quantity`, `status`, `expires_at`, optional terminal timestamp,
`idempotency_key`, and `created_at`. `(order_id, variant_id)` is unique.
Reservation statuses are `active`, `consumed`, `released`, and `expired`.

`public.inventory_movements` is append-only and contains `id`, `variant_id`,
`movement_type`, nonzero `on_hand_delta` or `reserved_delta`, balances after the
movement, optional `reservation_id`, optional `order_item_id`, optional
`actor_id`, required idempotency key, optional reason, and `created_at`.

Reservation, release, expiry, and consumption operations lock the authoritative
rows or use equivalent conditional atomic updates. Stock finalization is
exactly once.

## Carts and Addresses

Checkout is authenticated-only. Guests may browse and keep a local client cart,
but authentication is required before server checkout and order creation.

`public.carts` contains `id`, `user_id`, `created_at`, and `updated_at`, with
`UNIQUE(user_id)`. There is one persistent cart per authenticated user.

`public.cart_items` contains `id`, `cart_id`, `variant_id`, positive `quantity`,
`created_at`, and `updated_at`, with `UNIQUE(cart_id, variant_id)`. Cart prices,
discounts, inventory, and totals are never authoritative and are not stored as
truth.

`public.addresses` contains `id`, `user_id`, optional `label`, `recipient_name`,
`phone`, `address_line1`, optional `address_line2`, optional `barangay`,
`city_municipality`, `province`, `postal_code`, two-letter `country_code`
defaulting to `PH`, `is_default`, `created_at`, and `updated_at`. A partial
unique index permits at most one default address per user.

## Orders

`public.orders` contains `id`, unique `order_number`, nullable `user_id`, unique
`idempotency_key`, `status`, currency and order totals, recipient/address
snapshots, optional customer note, cancellation/delivery-failure reasons,
`placed_at`, `created_at`, and `updated_at`.

Persisted order statuses are exactly:

```text
CONFIRMED
PROCESSING
PACKING
READY_FOR_SHIPMENT
SHIPPED
IN_TRANSIT
OUT_FOR_DELIVERY
DELIVERED
COMPLETED
CANCELLED
DELIVERY_FAILED
```

There is no persisted order draft and no payment-derived order status. The cart
is the pre-order state. Payment status remains independent.

Order number format is `ORD-YYYYMMDD-XXXXXXXXXX`, using database UTC date and a
trusted 10-character uppercase hexadecimal random suffix. It is unique,
nonsequential, never browser-generated, retried on collision, and not a
security credential.

Order snapshots contain customer email, recipient name/phone, address lines,
barangay, city/municipality, province, postal code, and country code. They do
not depend on a live address FK.

`public.order_items` contains nullable catalog FKs plus immutable product name,
variant name, SKU, selected-options object, positive quantity, unit prices and
discounts, line totals, and `created_at`. Catalog deletion uses `SET NULL`; the
snapshots survive.

`public.order_status_history` is append-only and contains `id`, `order_id`,
optional `from_status`, `to_status`, optional note, source, optional
`changed_by`, unique transition idempotency key per order, bounded metadata, and
`created_at`. Customers cannot insert history directly.

### Customer Progress

Customer stage is derived and not persisted:

| Customer stage | Internal states |
| --- | --- |
| `CONFIRMED` | `CONFIRMED` |
| `PREPARING` | `PROCESSING`, `PACKING`, `READY_FOR_SHIPMENT` |
| `SHIPPING` | `SHIPPED`, `IN_TRANSIT` |
| `ARRIVING` | `OUT_FOR_DELIVERY` |
| `DELIVERED` | `DELIVERED`, `COMPLETED` |

Payment review/rejection, cancellation, delivery failure, and future
return/refund states are exception overlays, not successful stages.

### Order Transitions

Allowed success transitions are:

```text
initial -> CONFIRMED
CONFIRMED -> PROCESSING
PROCESSING -> PACKING | READY_FOR_SHIPMENT
PACKING -> READY_FOR_SHIPMENT
READY_FOR_SHIPMENT -> SHIPPED
SHIPPED -> IN_TRANSIT | OUT_FOR_DELIVERY
IN_TRANSIT -> OUT_FOR_DELIVERY
OUT_FOR_DELIVERY -> DELIVERED
DELIVERED -> COMPLETED
```

Cancellation is allowed from `CONFIRMED`, `PROCESSING`, `PACKING`, and
`READY_FOR_SHIPMENT` through an authorized operation. Delivery failure is
allowed from `SHIPPED`, `IN_TRANSIT`, or `OUT_FOR_DELIVERY`. Authorized
redelivery may move `DELIVERY_FAILED` to `IN_TRANSIT` or
`OUT_FOR_DELIVERY`; final failure may move it to `CANCELLED`. `COMPLETED` and
`CANCELLED` are terminal. No backward successful transition is allowed.

Manual GCash requires payment `PAID` and reservation `consumed` before
`CONFIRMED -> PROCESSING`. COD may enter `PROCESSING` while payment is `UNPAID`
after its reservation has been consumed. Cancellation never implies a payment
refund or automatic physical restock.

## Payments

`public.payments` contains `id`, unique `order_id`, method, status,
`amount_minor`, `currency_code`, unique idempotency key, optional `paid_at`,
`created_at`, and `updated_at`. Methods are `COD` and `MANUAL_GCASH`.

There is exactly one payment row per order. Retries and proof corrections use
submissions/events rather than additional canonical payment rows.

Payment statuses are:

```text
UNPAID
SUBMITTED
VERIFYING
PAID
FAILED
REJECTED
REFUND_PENDING
PARTIALLY_REFUNDED
REFUNDED
```

Refund statuses are reserved but unavailable to Phase 1 operations because the
refund workflow is deferred.

`public.payment_submissions` contains `id`, `payment_id`, `submitted_by`,
`claimed_amount_minor`, optional non-unique reference number, unique receipt
storage path, submission review status, optional reviewer/timestamp/rejection
reason, idempotency key unique within the payment, and `created_at`.

Payment evidence is immutable. Every corrected proof creates a new submission
row and new receipt object. Prior evidence, review result, and rejection reason
remain unchanged.

`public.payment_events` is append-only and contains `id`, `payment_id`, optional
`submission_id`, event type, optional `from_status`, `to_status`, optional
actor/reason, unique idempotency key per payment, bounded metadata, and
`created_at`.

Allowed Phase 1 payment transitions are:

```text
initial -> UNPAID
UNPAID -> SUBMITTED                 (timely GCash proof)
UNPAID -> PAID                      (trusted COD settlement)
UNPAID -> FAILED                    (trusted terminal resolution)
SUBMITTED -> VERIFYING | REJECTED | FAILED
VERIFYING -> PAID | REJECTED | FAILED
REJECTED -> SUBMITTED               (new proof within valid retry window)
```

`FAILED` is terminal in V1. Customers can submit evidence but cannot directly
change payment state or establish `PAID`.

## Manual GCash and Reservation Lifecycle

Canonical flow:

```text
Checkout:
order = CONFIRMED
payment = UNPAID
reservation = active
expires_at = checkout time + 2 hours

Proof submitted before expiry:
new immutable payment submission and receipt object
payment = SUBMITTED
reservation remains active
expires_at = submitted_at + 24 hours

Review begins:
payment = VERIFYING

Approval:
payment = PAID
reservation = consumed
order may enter PROCESSING

Normal proof rejection:
payment = REJECTED
order remains CONFIRMED
reservation remains active while retry deadline is valid

Corrected proof:
new immutable submission and receipt object
payment = SUBMITTED
```

A normal rejection never automatically cancels the order or releases stock
while the retry deadline is valid.

The two-hour initial TTL and 24-hour proof-review hold are configured once by
trusted server processing; only the resulting `expires_at` is persisted. The
verification hold is derived from an active reservation plus payment
`SUBMITTED` or `VERIFYING`; no duplicate reservation status is needed.

### Final Timeout Resolution

Elapsed time identifies a candidate for resolution but never proves that money
was not received. At the effective deadline:

1. Lock the payment, order, reservation, and inventory rows.
2. Revalidate payment, order, reservation status, and deadline.
3. Stop if payment is `PAID`, reservation is not active, or state has changed.
4. If evidence may represent received but unverified money, surface mandatory
   admin resolution; do not automatically reject or release.
5. If no proof was submitted, trusted closure may move `UNPAID` to `FAILED`
   with a proof-window-closed reason; this closes the attempt and does not claim
   that external money movement was disproved.
6. If the latest proof is already `REJECTED`, final closure leaves payment
   `REJECTED`.
7. If payment is `SUBMITTED` or `VERIFYING`, an authorized reviewer must decide
   `PAID` or `REJECTED`; timeout alone cannot choose either result.
8. A trusted final rejection/closure releases or expires the reservation,
   cancels the order where applicable, appends payment and order history, and
   appends an audit event in one transaction.

No release may rely only on a stale expiry candidate query. Overdue
`SUBMITTED`/`VERIFYING` rows form a derived admin queue and require explicit
resolution; the V1 operating contract does not permit indefinite unresolved
holds.

Reservation transitions are exactly:

```text
active -> consumed
active -> released
active -> expired
```

All terminal states are final. Exact retries are idempotent; conflicting
terminal attempts fail without side effects.

For COD, the reservation is consumed when the order is authoritatively accepted
because settlement occurs later. A later cancellation/restock uses explicit
audited inventory movement, never reservation reversal.

## Audit

`public.audit_logs` is append-only and contains `id`, optional `actor_id`,
optional actor-role snapshot, action, entity, optional entity ID, bounded
old/new values, optional request ID, optional IP address/user agent, bounded
metadata, and `created_at`.

Audit privileged role changes, inventory mutations, order corrections, payment
review/state changes, final timeout resolution, and authorization changes. Do
not store secrets, tokens, signed URLs, receipt contents, full request bodies,
or unbounded provider payloads. Phase 1 has no automatic audit deletion.

## Storage Foundation

Phase 1 creates/configures exactly two buckets:

| Bucket | Phase 1 contract |
| --- | --- |
| `product-images` | Public read; trusted administration write |
| `payment-receipts` | Private; authorized signed upload/read |

`return-proofs` is explicitly deferred until the returns workflow exists and is
not created or configured in Phase 1.

Paths are:

```text
product-images/products/{product_id}/{uuid}.webp
payment-receipts/{user_id}/{order_id}/{uuid}.webp
```

Receipt defaults are a 2 MB maximum and JPEG, PNG, or WebP content. Trusted
validation checks actual signature/content, MIME declaration, extension, size,
owner, business association, path, and upload purpose. Private reads use a
short-lived single-object signed URL; paths and signed URLs are not
authorization. Signed URLs are not stored.

Receipts are retained as financial/support evidence until a formal policy is
approved. Phase 1 performs no automatic receipt deletion.

## RLS and Browser Capabilities

| Tables | Classification | Browser capability |
| --- | --- | --- |
| `profiles` | Mixed | Owner select; update allowlisted profile fields |
| `private.user_roles` | Server only | No direct browser access |
| Catalog/options/images | Public read/admin managed | Read only published/active catalog; no browser writes |
| Inventory/movements/reservations | Server only | No browser access |
| `carts`, `cart_items` | Customer owned | Owner CRUD under RLS |
| `addresses` | Customer owned | Owner CRUD under RLS |
| Orders/items/history | Mixed | Owner read; trusted server writes |
| `payments` | Mixed | Owner-safe read; trusted server state writes |
| `payment_submissions` | Mixed | Owner read; creation through authorized server flow |
| `payment_events` | Server only | No direct browser access |
| `audit_logs` | Server only | No browser access |

Parent ownership is rechecked through authoritative relations; supplied IDs are
never trusted. Admin writes use authenticated server operations rather than
broad direct browser policies. Server-only tables receive no meaningless
browser policies.

## ACL and Authorization Helper

Revoke default object privileges from `PUBLIC`. Grant only required schema
usage and operations. Browser roles receive no inventory, order-state,
payment-state, role, event, or audit DML. Revoke default function execution in
project-owned schemas and explicitly grant each callable function.

The only role predicate is:

```text
private.has_role(required_role TEXT)
```

It derives the subject only from `auth.uid()`, returns false when unauthenticated,
rejects unsupported role names, is `STABLE`, and uses `SECURITY DEFINER` only to
avoid role-table RLS recursion. It has a fixed minimum-privilege owner, empty
search path, fully qualified references, no dynamic SQL, and execution revoked
from `PUBLIC` and `anon`. Grant `authenticated` only the schema usage and
execute permission required by RLS. The `private` schema is not Data API
exposed.

Every `SECURITY DEFINER` function must document necessity, fix its owner and
empty search path, fully qualify objects, validate inputs, avoid dynamic SQL,
revoke default execution, grant only intended roles, and have unauthorized
execution tests. Trigger functions have no direct application-role execute
grant. Atomic commerce functions are executable only by the Supabase
`service_role` database role used by authorized server processing.

## Deletion and Historical Retention

Deleting an Auth identity may cascade profile, roles, cart, cart items, and
addresses. It must not delete orders, order snapshots/history, payments,
submissions/events, inventory movements, or audit records. Historical actor and
customer FKs use `ON DELETE SET NULL`; snapshots retain business facts.

Orders and their history, reservations, and payments use restrictive deletion.
Catalog FKs in order items use `SET NULL`; catalog snapshots survive. Payment
evidence rows and financial history do not cascade away. Storage object deletion
is explicit and separately authorized.

## Index and Uniqueness Contract

PK and unique constraints supply indexes for slugs, SKU, order number,
idempotency keys, one cart per user, one cart-item variant, one payment per
order, storage paths, and option joins. Add only query-driven indexes:

```text
categories(parent_id)
products(category_id, status)
product_variants(product_id, status)
product_images(product_id, position)
product_options(product_id, position)
product_option_values(option_id, position)
inventory_movements(variant_id, created_at desc)
inventory_reservations(variant_id, status)
inventory_reservations(expires_at) where status = 'active'
orders(user_id, created_at desc)
orders(status, created_at desc)
order_items(order_id)
order_status_history(order_id, created_at desc)
payment_submissions(payment_id, created_at desc)
payment_events(payment_id, created_at desc)
audit_logs(entity, entity_id, created_at desc)
```

GCash reference numbers are not unique. Future promotion codes are
case-insensitively unique only when promotions are implemented.

## Updated-At Handling

Use one generic trigger function for mutable rows only: profiles, categories,
products, variants, inventory, carts, cart items, addresses, orders, payments,
and payment submissions. Do not attach it to append-only movements, histories,
events, or audit logs.

## Realtime Preparation

Realtime is not activated in Phase 1. Stable PKs, ownership columns, history,
indexes, and RLS prepare later private subscriptions. Do not add publication
membership, Broadcast triggers, outbox tables, channels, or provider events.
Canonical database fetches remain authoritative.

## Migration Sequence

Phase 1B authors migrations in this dependency order:

```text
0001_foundation_identity
0002_catalog
0003_customer_cart_addresses
0004_orders
0005_inventory
0006_payments_audit
0007_security_rls_grants
0008_storage_foundation
```

Orders precede inventory because reservations and movements reference orders and
order items. All relations/functions precede final policies and grants. Storage
follows payment ownership and authorization foundations.

Phase 1B is local-first: `supabase init`, then `supabase start`, then migration
authoring and replay. It must not link or mutate a hosted project.

## Verification Requirements

Schema tests cover table/column types, checks, money equations, FKs, delete
behavior, uniqueness, indexes, valid transitions, and append-only behavior.

Authorization tests prove customers cannot self-promote, write prices or stock,
read another customer profile/order/payment/receipt, set `PAID`, append history,
or write audit logs. Private helper execution and search-path attacks require
negative tests.

Transaction tests cover authoritative checkout, order/history transitions,
payment submission/review, final timeout resolution, and idempotent retries.
Concurrency tests run simultaneous last-item reservations and conflicting
consume/release/expire attempts. Storage tests cover public product reads,
trusted writes, receipt privacy, content/size/path validation, immutable proof
resubmission, and signed URL authorization.

Fresh local replay must succeed from zero, replay cleanly, and produce no
unexplained schema diff. Financial, authorization, transaction, and concurrency
checks are release-blocking.
